The Hacker Newsは、GitHub Actionsのactions-cool/issues-helperで、既存タグが通常の履歴に見えない偽装コミットへ付け替えられ、ワークフロー実行時に認証情報を収集して外部送信するコードが動いたと報じた。タグ指定でこのActionを利用していた組織では、ソースコードを変更していなくてもCI/CDの実行経路だけが汚染され、リポジトリ権限を持つトークン、クラウド鍵、配布用認証情報などが露出した可能性がある。攻撃者視点では、開発者端末を直接侵害せずに正規の自動化基盤から秘密情報を抜けるため、後続のリポジトリ改ざん、パッケージ公開、クラウド侵入へ広がりやすい。確認すべき範囲は該当Actionの利用有無、タグ参照の有無、問題期間中のワークフロー実行履歴、外部送信先への通信、Secretsの使用実績まで及ぶ。現時点で、リポジトリ侵害の手口、影響したタグごとの期間、実際に窃取された秘密情報の範囲は未確認として扱う必要がある。

深掘り解説

GitHub Actionsのタグ固定は固定ではない

GitHub Actionsで<code>uses: owner/repo@v1</code>のように指定すると、見た目は特定バージョンを固定しているように見える。しかしタグはGitの参照名であり、管理者権限やリポジトリ侵害により別のコミットへ動かせる。つまり、レビュー済みのワークフロー定義が変わらなくても、実行されるコードだけが差し替わる余地が残る。 この性質は、通常のアプリケーション依存関係より検知が難しい。例えば、ある組織が<code>actions-cool/issues-helper@v3</code>を複数リポジトリで使っていた場合、各リポジトリの差分には何も出ない。一方で、次回のissue処理や定期実行で偽装コミットのコードが動き、<code>GITHUB_TOKEN</code>やクラウド公開用の鍵を読み取る可能性がある。監査では、ワークフローYAMLの変更履歴だけでなく、実行時に解決されたActionのコミットSHA、ジョブログ、外向き通信、Secrets参照の有無を合わせて見る必要がある。 防御の基本は、信頼境界を「自組織のワークフロー定義」ではなく「実行されるActionの実体」まで広げることにある。重要なパイプラインではタグではなくフルコミットSHAで固定し、Dependabotや内部レビューで更新を管理する。すべてをSHA固定できない場合でも、外部Actionの利用台帳、許可リスト、最小権限の<code>GITHUB_TOKEN</code>設定、環境ごとのSecrets分離を組み合わせると、侵害時の到達範囲を狭められる。初動ではActionを無効化するだけで終えず、該当期間に実行されたワークフローで使われた秘密情報を失効し、後続の不審なコミット、リリース、パッケージ公開まで追跡する必要がある。
