深掘り解説

CI/CD の権限は「自動化の便利さ」ではなく「侵害の伝播範囲」で考える

CI/CD は、開発を速くする仕組みである一方、攻撃者から見ると「秘密情報が集まり、しかも自動で動く」高ROIの場所となる。ここで問題になるのは、単にパイプラインが実行されることではなく、何にアクセスできるか、どの範囲まで成果物を出せるか、どの変更が本番に届くかという伝播範囲の広さとなる。 例えば、ある npm パッケージの更新時に GitHub Actions が走り、そこで取得したトークンで別のリポジトリの成果物を更新できる構成があるとする。攻撃者がそのパッケージを汚染できれば、開発者端末を直接奪わなくても、CI 上で秘密情報を抜き取り、署名前の成果物を書き換え、さらに下流の利用者へ再配布する流れを作れる。被害は「1個のリポジトリの不具合」に見えても、実際には複数システムにまたがる。 実務では、まず「このワークフローは本当にその権限が必要か」を点検する。読み取り専用で足りる場面に書き込み権限を与えていないか、公開パッケージの更新時に社内秘密を読める設定になっていないか、タグやリリース作成を誰が起点にできるかを確認する。具体例として、テスト用のジョブに本番配布トークンが渡されている構成は危険度が高い。テストの失敗や外部からの依存汚染が、そのまま本番配布の乗っ取りに変わるためとなる。 封じ込めの観点では、最初に止めるべき場所は端末ではなく、トークン、ワークフロー、公開レジストリへの配布経路になる。ログとしては、見慣れないパッケージ更新、Actions の不審な外部通信、短時間の大量シークレット参照、通常と異なるリリース生成を重点的に見る。被害の広がりを抑えるには、依存関係の固定とレビュー、CI の最小権限化、配布前の署名や差分確認を組み合わせる必要がある。
