概要

ノルウェー国家安全保障機関（NSM）は、Microsoft Azure API Management（APIM）の脆弱性が複数の企業に影響し、Microsoftが修正したと明らかにした。未知の攻撃者はAPIM内のアクセストークン、秘密情報、名前付き値へのアクセスを積極的に試みており、単なるサービス停止ではなく、連携先への認証情報の取得を狙う動きとして扱う必要がある。影響先にはエネルギー企業のEquinorやSkagerak Energiが含まれるが、入力情報だけでは攻撃成立に必要な構成や具体的な侵入経路は確認できず、同種の構成を持つ組織への波及範囲も特定できない。取得された情報があれば、権限や有効期間に応じて、API経由のデータ参照や後続システムへの操作に悪用されるおそれがある一方、実際の窃取や不正利用の有無は未確認となる。修正適用だけで完了とせず、APIMの構成・監査記録、秘密情報へのアクセス履歴、関連トークンの利用状況を照合し、影響が疑われる認証情報の失効・更新まで確認する必要がある。

📌 キーワード解説

Azure API Management（APIM）

APIへの認証や流量制御を集約する仕組み。アプリ単体の侵害と異なり、保管情報を通じ複数の連携先へ影響が及び得る。

名前付き値（Named Values）

APIMのポリシー等から参照する設定値で、秘密情報を含む場合がある。通常の設定値と違い、漏えい時は認証情報として扱う必要がある。

アクセストークン

サービスへのアクセス権を示す資格情報。パスワード変更だけでは無効化されない場合があり、失効・更新の確認が要る。

深掘り解説

秘密情報の露出対応は修正適用と資格情報の失効を分けて考える

脆弱性の修正は、攻撃者が同じ入口を再利用する危険を下げる対策であり、すでに読み取られた秘密情報を無効化する対策とは別に扱う必要がある。APIMのような中継基盤では、一つのトークンが複数のAPIや後続サービスで使われていることがあり、窃取の有無を確認できない場合も安全側の判断が必要になる。 例えば、APIMの名前付き値に顧客データ基盤向けのトークンが保存されていた場合、修正適用後もそのトークンが有効なら、攻撃者は脆弱性を再利用せずにAPIへアクセスできる。対象となる値の用途と権限を特定し、発行元で失効・再発行したうえで、利用ログに不審な送信元、通常と異なる呼び出し量、未使用だったAPIへのアクセスがないかを確認する。更新時は業務連携の停止を避けるため、依存先と切替順序を調整し、旧トークンが残存していないことまで検証する。
