VU#456290: Hugging Face Transformers library writes remote code to disk prior to consent check

Impact判定理由

認証不要の遠隔コード実行ではないが、未信頼リポジトリを読むだけで不正な Python ファイルがローカルに残り、共有キャッシュ環境では後続処理へ波及し得るため影響は大きい。実行前の制御をすり抜けて永続物を置ける点が運用上重く、AI/ML 基盤や検証環境では実被害の起点になりやすい。公的機関である CERT/CC の注意喚起であり、悪用可能性の現実性を踏まえてベース評価を一段強めている。

概要

Hugging Face Transformers の load_custom_generate() に、同意確認より先にリモートの Python ファイルを書き込んでしまう不備が見つかった。対象は 4.49.0 から 5.8.1 までで、custom_generate/generate.py を含むモデルを読み込むだけで、ユーザーが拒否しても ~/.cache/huggingface/modules に内容が残る。実行そのものは同意確認で止まるが、ディスク上への永続的な配置が先に起きるため、後続の信頼済み読み込みやキャッシュ再利用に影響が及ぶ余地がある。攻撃者は悪意あるモデルリポジトリを公開し、利用者の初回読み込みを踏み台にして不正ファイルを残せる。現時点ではベンダー修正は示されておらず、実際にどの条件で後続実行へつながるかは運用環境依存で未確認となる。

trust_remote_code

キャッシュ汚染

一度残った不正ファイルが後続処理へ混入する状態。単なる保存と違い、再利用されると影響が広がる。

リモートモジュール取得

外部リポジトリからコードを取り込む処理。モデル本体の取得と混同されやすいが、コードを含む点が危険になる。

深掘り解説

同意確認は「実行」だけでなく「書き込み」の前に置く必要がある

この事案の本質は、危険なコードを走らせたかどうかではなく、危険なコードを<strong>どの時点でローカルに残したか</strong>にある。多くの制御は「実行前に止めればよい」と考えがちだが、AI/ML 基盤ではキャッシュ、前処理済み資産、生成補助ファイルが後続処理の入力になるため、書き込み時点での統制が欠けると防御線を一段越えやすい。 具体例として、分析担当者が未信頼のモデルを試験環境で読み込んだだけで <code>~/.cache/huggingface/modules</code> にファイルが残り、その後に別のジョブや別ユーザーが同じキャッシュを参照すると、初回の拒否とは無関係に影響が波及し得る。ここで重要なのは、実行権限がなくても、共有キャッシュや永続ボリュームがあると被害面が組織内に広がる点にある。 運用上は、1) 外部取得前に同意判定を置く、2) キャッシュをユーザー単位・用途単位で分離する、3) 未信頼ソースからの取得後に残存物を監査する、の三点が効く。特に検証環境での動作確認を本番と同じホームディレクトリで行うと、検証のつもりが本番資産へ不正ファイルを持ち込むことがあるため、隔離と使い捨てが重要になる。AI 系ライブラリは「入力データの取り込み」と「コードの取り込み」が近接しやすく、ここを分けて設計できるかが事故率を左右する。
