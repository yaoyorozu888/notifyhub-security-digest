VU#738147: Vendor-signed UEFI Shell applications allow Secure Boot bypass

🗞️ CERT/CC 🕒 2026-09-23T03:13:12+09:00 🔗 原文を開く
Impact: High Vulnerability Disclosure
原文リンク 日次トップ

Impact判定理由

起動前の信頼境界を越えてSecure Bootを迂回できるため、成立するとOS起動前からの永続化や未署名コード実行につながる。EDRや通常のエンドポイント制御では見えにくく、被害の質は高い。\nCERT/CCの注意喚起であり、単なる理論上の欠陥ではなく、失効一覧DBXの適用やベンダー更新という実務対応が必要な段階にあるため、情報源補正で重みを上げた。

🧾 要約（ChatGPT / gpt-5.4-mini-2026-03-17）

概要

署名済みのUEFI Shellアプリケーションを悪用し、Secure Bootの検証を迂回できる問題が報告された。対象は、ベンダー証明書をDBで信頼している、または該当バイナリのハッシュを許可している端末となる。攻撃者はmmやdmpstoreのようなメモリ操作機能を足がかりに、起動前の状態を書き換えて未署名のUEFIコードを動かせる。成立には物理アクセスか管理者権限が前提になりやすく、一般的なEDRでは起動前の改変を見逃しやすい。影響は単なる設定変更にとどまらず、永続化やカーネル導入まで広がる可能性があるが、実際にどの機種へどこまで配布されているかは個別確認が必要となる。

📌 キーワード解説

Secure Boot

起動時に署名を検証する仕組み。OS起動後の制御ではなく、起動前の改変を防ぐ点が要点となる。

UEFI DB

起動を許可する証明書やハッシュの許可一覧。DBXの失効一覧と混同しやすいが、役割は逆方向となる。

DBX

起動を拒否する失効一覧。修正版配布だけでなく、古い署名済みバイナリを止めるにはここへの反映が必要となる。

EDR

OS起動後の監視が中心となる製品群。UEFI段階の改変は観測外になりやすい点が重要となる。

深掘り解説

起動前の信頼チェーンは、署名済みでも安全とは限らない

実務で見落とされやすいのは、「署名されているから安全」という判断が、実際には「起動してよい」と「やってよい」の区別を含まない点となる。たとえば、工場出荷時にベンダー署名されたUEFI Shellが端末に残っている場合、通常のOS管理者権限では触りにくい領域へ到達されることがある。攻撃者はそこからSecure Bootの状態やブートローダーを改変し、OS起動後の防御が始まる前に常駐化を狙える。具体例として、端末保守用に残したUEFIツールをそのまま信頼していると、出荷時の想定より広い操作権限を与えることになる。\n\n対策の勘所は二つある。一つ目は、署名済みコンポーネントの棚卸しを「存在確認」で終わらせず、どの機能を持つかまで見ることとなる。二つ目は、修正版配布だけでなくDBXでの失効反映を含めて、古い信頼を切れるかを確認することとなる。たとえば、配布済みの新しいShellがあっても、古い脆弱版が別経路で起動できるなら封じ込めにならない。CSIRTとしては、OS上の脆弱性対応と同じ速度感で扱わず、BIOS/UEFI更新、資産差分、失効一覧の適用状況まで一体で確認する必要がある。
