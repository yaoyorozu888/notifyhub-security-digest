概要

Casdoor の 認可バイパス が公開され、3.115.0 以前に影響がある。認可層は URL の ?id= を見て許可判定する一方、下流のコントローラは JSON 本文の所有者情報だけで処理するため、別の組織を対象にした操作が通ってしまう。多重テナント環境では、単一組織の管理者権限を取った攻撃者が、他組織のユーザー管理や権限変更、SSO/SAML の妨害へ広げられる。影響はテナント分離の崩壊まで及び、構成次第では Casdoor インスタンス全体の支配に近づく可能性がある。現時点では ベンダーパッチは未確認 で、どの公開エンドポイントが実際に到達可能か、運用側の権限設計がどうなっているかは要確認となる。

📌 キーワード解説

認可バイパス

権限判定だけ通して実処理が別対象に向く状態。認証漏えいとは別で、ログ上は正規操作に見えやすい。

多重テナント

1つの基盤で複数組織を分離運用する形。分離が崩れると、同一管理画面でも他組織へ横断影響が出る。

認可層と実処理の不整合

判定に使う対象と、実際に更新する対象がずれる問題。入力値の一部だけを信じる実装で起きやすい。

深掘り解説

認可判定は「見た値」と「触る値」を一致させる必要がある

この種の不具合で本質的に危ないのは、権限チェックが通ったかではなく、**何を根拠に通したか**と**何を変更したか**がずれる点にある。Casdoor の例では、認可層は URL の <code>?id=</code> を見て許可を判断するが、下流は JSON 本文の owner や name を見て別対象を更新しているため、攻撃者は「認可では A を見せ、実処理では B を触る」形で境界を越えられる。 運用上は、API の入力仕様が複数箇所で再解釈されていないかを疑う必要がある。たとえば管理画面から「組織 A のユーザー削除」を実行したつもりでも、リクエスト改変で本文の対象だけ差し替えられる設計なら、監査ログには通常の管理操作として残る可能性がある。すると検知は難しく、後追い調査でも「正規管理者が操作したように見える」状態になりやすい。 具体例として、テナント型 IdP で組織 A の管理者権限を取った攻撃者が、組織 B の SSO 設定を削除できれば、B の業務停止や認証経路の改ざんにつながる。ここで重要なのは、被害が単なる個別ユーザー削除にとどまらず、権限管理や認証基盤そのものへ波及する点にある。したがって、実務では「管理 API が本当に組織境界を固定しているか」を、実装とログの両面で確認する姿勢が必要になる。
