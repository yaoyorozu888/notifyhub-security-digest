Impact判定理由

侵害済みの service principal を足がかりに Azure リソースを削除しており、機密窃取よりも事業停止と復旧妨害の影響が大きい。単一資産ではなく、リソースグループや関連設定まで巻き込むと被害が広がるため、運用上の深刻度は高い。メディア由来の二次情報ではあるが、Microsoft が追跡名を付けている事案で、悪用の現実性は高く据え置き以上で見るのが妥当になる。

概要

Microsoft Azure 環境で、侵害済みの service principal を使って リソース削除 が行われた事案が報じられた。攻撃者は JADEPUFFER と関連付けられ、Microsoft は Storm-3168 として追跡している。実行時間は約18時間で、認証情報を奪った後に管理権限に近い操作へ進み、復旧コストを伴う破壊的行為へ移ったとみられる。典型的なランサムウェアとは異なり、暗号化よりも インフラ破壊 と事業停止を狙う点が重要になる。公開情報だけでは、侵入経路、奪取された権限の範囲、削除対象の全容は未確認であり、横展開や他リージョンへの波及の有無もまだ断定できない。

この種の攻撃は、単一VMの停止ではなく、RG、ストレージ、ネットワーク、監査基盤まで巻き込むと復旧が長期化しやすい。特に自動化用の service principal は人の監視が薄く、異常な削除操作が見逃されやすい。検知では、Azure Activity Log の Delete 系操作、権限付与の変化、短時間の大量操作を重点確認する。封じ込めでは、対象 principal の失効、ロール割り当ての棚卸し、削除保護とバックアップの健全性確認が先になる。

service principal

アプリや自動化用の識別子と権限の組み合わせ。人のアカウントより監視が薄く、侵害されると操作が広がりやすい。

Azure Activity Log

Azure の操作履歴を残すログ。監査ログと違い、削除や権限変更の追跡に直結し、異常操作の起点を見つけやすい。

リソースグループ

Azure の管理単位。VMだけでなく関連設定もまとめて消えるため、単体資産より被害が大きくなりやすい。

深掘り解説

自動化用主体は「便利な管理権限」ほど危ない

service principal は、手作業の代わりに Azure を操作するための主体であり、運用が成熟するほど権限が強くなりやすい。ここでの落とし穴は、通常のユーザーと違って、人のログイン失敗やMFAで止める発想が効きにくい点にある。 実務では、まず「何ができる主体か」ではなく「何をしてよい主体か」を絞る必要がある。たとえば、バックアップ取得だけの自動処理に、リソース削除やロール変更まで許す必要はない。権限が広いほど、侵害後の攻撃者は復旧妨害まで一気に進める。 具体例として、定期レポート用の自動化アプリが ReadOnly で足りるのに Contributor を持っていた場合、侵害者は仮想マシン停止、ストレージ削除、監査設定改変へと進める。逆に、最小権限と有効期限付き資格情報、操作対象の厳格な分離があれば、奪取されても被害の上限を下げやすい。 CSIRTが見るべきは、侵害の有無だけでなく、侵害された主体がどこまで壊せるかという観点になる。人のアカウントより発見が遅れやすい分、定期的な棚卸しと異常操作の監視を前提に設計する必要がある。
