GitHub 'Verified' Commits Can Be Rewritten Into New Hashes Without Breaking Signatures

概要

GitHub の Verified 付きコミットでも、署名を壊さずに別のハッシュへ書き換えられる可能性が示された。見た目の差分や作者情報、日時が一致していても、ハッシュ値だけが異なる別物を作れる点が論点になる。これにより、レビュー担当者が署名と表示だけを頼りにすると、同じ内容に見える複数の履歴を見落とすおそれがある。実害は、改ざん済み履歴の混入、監査証跡の曖昧化、内部承認フローのすり抜けにつながる形で広がる。なお、記事要約だけでは対象条件、GitHub 側の検証仕様、再現手順の細部は未確認であり、どの運用で実際に問題化するかは追加検証が必要になる。

📌 キーワード解説

コミットハッシュ

内容の識別子だが、署名の正当性とは別軸になる。同一内容に見えても別ハッシュを持てる点が混同されやすい。

署名付きコミット

改ざん防止の根拠として使われるが、履歴の一意性を完全には保証しない。検証表示だけで同一性を断定しない。

Verified 表示

GitHub 上の検証済み表示で、署名検証の結果を示す。安全な履歴そのものを保証する印ではない。

深掘り解説

署名の検証と履歴の同一性は別問題

Git の運用では、署名が通ることと、そのコミットが唯一無二の履歴であることを同じ意味に扱いがちになる。しかし実際には、署名は「その鍵の所有者が作った」ことの証拠であり、履歴の完全な固定を意味しない場面がある。 ここで重要なのは、レビューや監査の判断軸を「Verified だから安全」から一段分けて考えることになる。たとえば、同じファイル内容・作者・日時でも別ハッシュのコミットが成立するなら、差分レビューが同一性の担保になっていない可能性が出る。承認済みの変更を後から別履歴へ差し替えられると、追跡や説明責任が崩れる。 具体例として、社内のリリース手順で「署名済みタグと Verified コミットがあること」を条件にしている場合を考える。もし確認対象が表示上の署名結果だけなら、同じ見た目の別ハッシュを別経路で混入させても見逃す余地がある。対策としては、署名状態に加えて、参照しているハッシュ、タグ、取得元、ビルド入力の固定を確認する運用が必要になる。
