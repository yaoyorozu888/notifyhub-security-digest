概要

Fastjson 1.x の脆弱性が、認証不要のRCE として攻撃に使われているという報道である。対象は主に Spring Boot を含む Java アプリケーションで、細工された JSON リクエストにより、Java プロセス権限 で任意コード実行へつながる。記事では CVE-2026-16723 として扱われ、Alibaba 付与の CVSS は 9.0 とされるが、実運用上は「脆弱な Fastjson 1.x を使い続けているか」「外部から JSON を受けるか」が重要な分岐になる。現時点で確認できるのは攻撃対象化の事実までで、恒久的な修正手段の有無、影響を受ける Fastjson の細かな条件、実際の侵害範囲は未確認である。公開 API、管理画面、社内向け業務 API のいずれでも入口になり得るため、1 台のアプリ侵害がそのまま横展開や資格情報窃取に接続しやすい。

深掘り解説

Java の JSON 変換で起きる「入力の境界」問題

JSON ライブラリの脆弱性は、単に「データを読む処理」が壊れるだけでは済まない。アプリが受け取った JSON をどこまで信頼し、どの段階でオブジェクト生成や型解決、参照解決を許すかで、攻撃面が大きく変わる。 実務で見るべきは、ライブラリ名そのものより「外部入力がそのまま変換器に入る経路」があるかどうかになる。たとえば、公開 API が JSON を受け取り、その値をログやDB登録ではなく内部オブジェクトとして即時に復元している場合、細工された入力が処理系の深い部分まで届きやすい。 具体例として、業務 API が受けた JSON を Fastjson 1.x で直接パースし、後続処理でそのオブジェクトをそのまま利用しているとする。このとき、入力検証が薄いまま型や参照の解決が走ると、アプリの想定外のクラス経由で副作用が出る余地が生まれる。逆に、JSON をいったん単純な値に落としてから厳格に検証する設計なら、同じライブラリでも被害の入り口は狭くなる。 CSIRT の観点では、パッチ有無だけでなく「どのサービスが Fastjson 1.x を使い、外部から JSON を受け、しかも到達可能か」を切り分けることが重要になる。公開 API と社内限定 API では優先度が変わるため、ライブラリの版数管理と通信経路の棚卸しを同時に進める必要がある。
