AI エージェントの権限を利用した情報漏えいにつながり、利用者の操作に見える形で社内データが外部へ流れる点が重い。既定設定では異常検知が効きにくく、被害は単発の漏えいではなく広い業務データへ及ぶ余地がある。媒体記事由来の二次情報ではあるが、Microsoft の研究として具体的な攻撃面を示しており、運用上は高めに見る妥当性がある。

概要

Microsoft の研究は、MCP の tool description に細工を入れるだけで、AI エージェントが利用者の代理として社内データを外部へ渡してしまう可能性を示した。攻撃者は正面突破せず、ツール説明文に誘導を埋め込み、エージェントの通常業務に見える処理として実行させる点が特徴となる。明示的なルール違反が見えにくいため、既定設定の監視では異常として拾いにくい。影響は、メール本文や文書要約など単発の情報漏えいにとどまらず、権限付きエージェントが扱う社内検索結果や業務データ全体へ広がる余地がある。一方で、どの程度の製品実装で再現するか、外部送信の抑止がどこまで効くかは、記事断片だけでは未確認となる。

MCP

AI エージェント

指示を受けて自律的に操作を進める仕組み。チャットボットと違い、実データ参照や外部送信まで踏み込みやすい。

tool description

ツールの用途を説明する文。実装によっては指示源として扱われ、説明文の汚染がそのまま挙動改変につながる。

深掘り解説

AI エージェントは「何を見せるか」より「何を実行できるか」で評価する

この種の問題で見落としやすいのは、攻撃者がモデル本体を壊さなくても、周辺の説明文やメタデータを汚染するだけで結果を変えられる点にある。AI の判断は入力本文だけでなく、ツール一覧、権限、既定の送信先、会話履歴など複数の要素に引きずられるため、見た目が正しくても安全とは限らない。 実務では、まず「このエージェントが何にアクセスできるか」を棚卸しする必要がある。たとえば社内検索に接続したエージェントが、取得した文書をそのまま外部要約サービスへ渡せる構成なら、説明文の一部を通じて漏えい経路ができる。逆に、参照専用のエージェントで、出力先を社内に固定し、機密語を含む場合は送信前に遮断する設計なら、同じ攻撃でも被害は大きく下がる。 具体例を挙げると、経理担当のためのエージェントが「請求書確認用ツール」を使って社内ファイルを読み、結果を自動で外部のチャットに転記する運用があるとする。ここに細工された tool description が混ざると、利用者は通常の確認をしているつもりでも、機密番号や顧客情報が外へ出る可能性が生じる。したがって、AI の安全対策はモデルの精度評価だけでは足りず、ツールの登録経路、説明文の改ざん耐性、送信先制御、監査ログの4点を合わせて見る必要がある。
