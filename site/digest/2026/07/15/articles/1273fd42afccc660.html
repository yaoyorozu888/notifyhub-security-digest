概要

xAIの Grok Build 用コーディングCLIが、利用者が指示した対象ファイルだけでなく、Gitリポジトリ全体 と完全なコミット履歴まで xAI管理のGoogle Cloud Storage に送っていたと報じられている。研究者は version 0.2.93 を検証し、実際の送信内容を取得して git bundle を復元し、エージェントに読ませてはいけないと明示されていたファイルまで取り出せたとしている。攻撃というよりは 過剰収集 と 機密流出 の問題で、ソースコード、履歴、削除済み変更、コメントや設定差分まで広く露出する余地がある。影響は単一ファイルにとどまらず、秘密情報の埋め込みや過去の試行錯誤の痕跡から、組織の開発情報全体に波及しうる。現時点では、どの条件で常時この挙動が起きるのか、保存期間や二次利用の有無、修正済みかどうかは確認できていない。

Git bundle

クラウドストレージ

外部保管先として便利だが、送信範囲が広いと機密の集積点になる。通信経路の秘匿より、保存後の扱いが重要になる。

過剰収集

目的に必要な最小限を超えてデータを集めること。誤送信より厄介で、履歴や派生情報まで漏れる。

深掘り解説

AI開発支援ツールで最小権限と送信範囲を分けて考える

生成AIやコード補助CLIでは、便利さの代わりに「どこまで読ませるか」と「どこまで送るか」を切り分けないと事故になりやすい。今回の論点は、AIが参照した範囲ではなく、実際にはリポジトリ全体を外部に送っていた点にある。つまり、画面上で見えている入力単位が小さくても、裏側の収集単位が大きければ、管理上のリスクは一気に跳ね上がる。具体例として、社内で「このファイルだけ解析してよい」と運用していても、ツールが.git配下までまとめて送れば、秘密鍵の削除履歴や未公開機能の試行錯誤まで相手側に渡る可能性がある。実務では、①送信対象の実測、②除外設定の有無、③保存先と保持期間、④監査ログの取得可否を別々に確認する必要がある。ベンダー説明が「必要なものだけ扱う」となっていても、実装が一致しているとは限らないため、初回導入時は小さな検証用リポジトリで通信を観測し、想定外のメタデータや履歴が出ていないかを確認する流れが有効になる。
