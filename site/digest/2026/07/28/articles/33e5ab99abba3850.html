概要

Spring Boot の /actuator/heapdump が外部から見えると、アプリケーションのメモリ内容を示す heapdump.hprof を取得される可能性がある。これは障害解析向けの機能だが、実際には APIキー、DBパスワード、接続先情報など、後続侵害に使える秘匿情報が含まれやすい。攻撃者はこれを拾って認証を回避し、管理画面やバックエンドへ横展開する狙いを取りやすい。影響は単一アプリに閉じないことが多く、同じ資格情報を使い回していれば周辺システムへ広がる余地がある。記事は観測報告であり、特定の脆弱性番号や新規ゼロデイの提示ではないため、どの環境で公開されていたかは未確認のまま残る。

📌 キーワード解説

heapdump

Java のメモリ採取結果。core dump に近いが、文字列として秘密情報を拾いやすい点が危険になる。

Spring Boot Actuator

運用用の診断口。便利だが、認証なし公開と静的な防御設定の差がそのまま露出につながる。

秘密情報の露出

漏れたのは脆弱性そのものではなく認証材料になる点が要注意。設定不備と組み合わさると侵入口になる。

深掘り解説

診断用エンドポイントは「見えること」自体を危険として扱う

診断用の機能は、動いているかよりも『外部から到達できるか』を先に確認する必要がある。理由は単純で、障害解析のための出力が、そのまま攻撃者の索引になるからになる。 たとえば /actuator/heapdump が公開されていると、アプリの内部状態を丸ごと取得される可能性がある。ログや設定ファイルでは見えない一時トークン、接続先、ライブラリ内部に残った資格情報が含まれることがあるため、侵害の起点としてはかなり効率がよい。攻撃者はこれを拾ってから、同じパスワードでデータベースや管理APIへ入る、別システムへ転用する、といった順で被害を広げやすい。 実務では、対処を『機能を無効化するか』だけで考えると判断がぶれやすい。まずは公開面の棚卸しを行い、認証前に到達できる診断口を閉じる、閉じられないなら経路制限を入れる、さらに秘密情報がメモリに残る前提で資格情報のローテーション計画を立てる、という順で整理するとよい。具体例として、開発では便利なため有効化した Actuator を本番へそのまま持ち込んだ結果、監視基盤の認証情報まで heapdump から回収される事案がある。こうなると、アプリ単体の復旧では終わらず、バックエンド全体の再発行が必要になる。
