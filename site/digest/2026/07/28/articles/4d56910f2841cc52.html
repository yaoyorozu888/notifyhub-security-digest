概要

n8n において、認証済みのワークフロー編集者が式評価のサンドボックスを抜け、n8n プロセス権限で OS コマンドを実行できる不具合が修正された。攻撃成立には編集権限が前提となるため、外部からの無差別侵入というより、管理画面への侵入後の悪用や内部不正、共有アカウントの悪用が主な入口になる。影響範囲は、同一ホスト上のファイル操作、資格情報の窃取、接続先システムへの横展開まで広がる可能性がある。記事では影響バージョンとして <2.31.5 と >=2.32.0,<2.32.1 が示されているが、実際の露出状況や既存の代替制御は未確認である。The Hacker News 経由の二次情報であり、再現条件や悪用の成熟度は一次情報で確認する必要がある。

深掘り解説

ワークフロー自動化基盤では、編集権限がそのまま実行権限に近づくことがある

n8n のような自動化基盤では、ワークフロー編集機能が単なる設定変更に見えても、内部では外部 API 呼び出し、テンプレート展開、式評価、シェル実行の前段をまとめて抱えやすい。ここでサンドボックスの境界が破れると、攻撃者は「画面を編集できるだけ」のつもりで入り、実際にはサーバー上の OS コマンド実行まで到達する。 実務で厄介なのは、権限設計がアプリ内のロールだけで完結していると、侵害後の動きが見えにくい点にある。たとえば、通常のログイン成功は監査上ただの編集操作に見え、そこから先のコマンド実行はアプリログに十分残らない場合がある。したがって、ワークフロー製品では「誰が編集できるか」だけでなく、「その編集がどの実行面に触れるか」を分けて評価する必要がある。 具体例として、運用担当者が一時的に編集権限を持つ共有環境を考えると、別サービスから漏れた資格情報で管理画面に入られただけで、バックアップの取得、環境変数の列挙、内部 API への到達が起こり得る。封じ込めでは、パッチ適用に加えて、編集者権限の最小化、監査ログの集中化、実行ノードの分離を同時に進める判断が重要になる。
