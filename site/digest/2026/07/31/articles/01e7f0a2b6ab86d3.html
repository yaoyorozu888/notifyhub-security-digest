概要

foreUP の REST API に、CVE-2026-15657 と CVE-2026-15658 の2件の脆弱性が見つかった。前者は顧客レコード応答に Finix の商取引認証情報 を平文で含め、後者は BOLA/IDOR により golfer_id を差し替えるだけで他人の個人情報や決済履歴を取得できる。攻撃には低権限の有効な利用者アカウントが必要だが、共有APIのため 同一テナント内だけでなく他施設の情報参照 にもつながる。ここから決済不正、個人情報流出、なりすまし、フィッシングの足場化まで広がる可能性がある。vendor は 2026-07-26 に修正済みと案内しているが、実際の悪用有無や流出範囲は本文では確認できない。

📌 キーワード解説

BOLA（Broken Object Level Authorization）

自分の権限外の個体を参照できる不備を指す。認証よりも、取得対象ごとの権限確認の抜けが問題になる。

IDOR（Insecure Direct Object References）

識別子を書き換えるだけで別人の資源に触れる状態を指す。BOLAと近いが、こちらは実装の露出しやすさを示す。

JWT（JSON Web Token）

認証済み利用者として API を呼ぶための票券に近い。盗まれると正規利用者に見えるため、権限境界の不備を直撃する。

深掘り解説

共有APIで起きる「低権限でも全部見える」事故の本質

今回の核心は、認証が通っていることと、見てよい個体がその利用者本人であることが別問題になっている点にある。API 側が「有効な JWT なら通す」だけで止まり、<code>golfer_id</code> ごとの所有確認を省くと、利用者Aが利用者Bの記録を列挙できる。 実務では、画面単位の権限設計よりも、API のオブジェクト単位の検査が抜けやすい。たとえば、会員サイトで自分の予約履歴を見せる機能がある場合、URL の ID を1増やしただけで他人の履歴が出るなら、その時点で機密情報の境界が崩れている。 さらに今回は、個人情報だけでなく決済トークンや商取引認証情報まで含まれている。つまり「閲覧されるだけ」で終わらず、別システムでの不正決済、フィッシング、問い合わせ窓口へのなりすましまで連鎖しやすい。API の修正が入っていても、既に取得された情報の失効、トークン再発行、監査ログの追跡が別作業として残る点に注意が要る。
