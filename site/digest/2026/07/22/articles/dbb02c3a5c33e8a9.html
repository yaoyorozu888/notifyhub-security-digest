概要

Plane の 1.3.0 以前に、マルチテナントの認可回避が見つかった。資産管理 API が workspace をまたいだアクセス制御を十分に確認せず、他ワークスペースのファイルを閲覧・削除・複製できる可能性がある。悪用には任意の Plane ワークスペースへの認証と、被害側の workspace slug と asset ID が必要になるが、これらは公開または半公開の URL、添付リンク、API 出力から拾われやすい。影響は単一ファイルの漏えいにとどまらず、業務データの破壊や、複製した資産を手元に残すことで痕跡を薄める動きまで広がり得る。CERT/CC はベンダーに連絡できておらず、修正パッチは未提供で、ネットワーク制御と監視での緩和が前提になる。未確認なのは、実運用での悪用事例、公開エクスプロイトの有無、影響範囲が 1.3.0 以外に及ぶかどうかになる。

📌 キーワード解説

マルチテナント

複数組織を同居させる構成を指す。単一組織前提の権限不備より、横断漏えいに直結しやすい。

認可回避

ログイン有無ではなく、対象資源への操作権限確認を飛ばす問題。認証済みでも他人のデータに触れる点が厄介になる。

workspace slug

URL上で作業領域を識別する文字列を指す。ID だけでなく slug も使うと、外部から推測される前提が強くなる。

プリサインドURL

期限付きで直接ファイルに触れる URL になる。認可の抜け穴があると、発行後の追跡と制御が難しくなる。

深掘り解説

マルチテナントの認可は「ログイン済みか」ではなく「その資源か」で見る

この事案で本質的なのは、認証の成否ではなく、<strong>対象の workspace に属する資源か</strong>を毎回確認していない点になる。多くの組織では「認証済みユーザーからの API 要求」を前提にしがちだが、そこに workspace slug や asset ID が混じると、実装の一部が別領域を参照していても見逃しやすい。結果として、攻撃者は自分の workspace に正常ログインしたまま、別 workspace の添付ファイルや成果物を操作できる。具体例として、公開された課題ページや共有リンクに含まれる slug と asset ID を拾い、自分の認証情報で削除要求を投げると、権限境界の外側にあるファイルでも消せてしまう。運用上の注意点は、画面の権限制御だけで安心せず、API の各エンドポイントで「workspace 所属確認」と「資源所有者確認」を分離して点検することになる。加えて、監査ログでは単なる失敗ではなく、<strong>他 workspace を指す識別子を含む要求</strong>を検知対象にする必要がある。こうした不整合は、機能追加時に起きやすく、後から UI を直しても API 側が残ると再発する。
