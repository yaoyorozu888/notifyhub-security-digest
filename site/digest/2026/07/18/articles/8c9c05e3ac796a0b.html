概要

NadMesh と呼ばれる Go 製ボットネットが、外部公開された AI 関連サービス を探して走査している。対象には ComfyUI、Ollama、n8n、Open WebUI、Langflow、Gradio などが含まれ、短期間に立ち上げられた検証環境や内部向け公開がそのまま残った構成を狙う流れとみられる。AWS キー や Kubernetes トークン を回収する設計が示されており、単なる露出探索ではなく、クラウド侵害や横展開の起点になりうる。被害は個別ホストの侵害に留まらず、認証情報の流用によるクラウド資源の不正利用、コンテナ基盤への再侵入、他環境への拡散へ広がる可能性がある。なお、実際の感染規模、盗取成功率、運用者の最終目的は記事断片だけでは未確認で、ダッシュボードの数値も自己申告に依存する点は留保が必要になる。

深掘り解説

外部公開した AI/自動化基盤は「便利さ」より先に認証境界を設計する

今回の焦点は、AI 推論やワークフロー基盤そのものではなく、それらを外部公開した瞬間に管理対象がどう変わるかにある。ComfyUI や Ollama、n8n のようなサービスは、開発者にとってはすぐ試せる一方で、攻撃者にとってはインターネットから直接触れる入口になる。特に危険なのは、画像生成やモデル実行の機能よりも、周辺に置かれた認証情報や接続設定が平文や半永続状態で残る場合になる。 実務上は「公開したかどうか」より、「何が見えているか」「何に触れられるか」を分けて考える必要がある。たとえば、検証用の Open WebUI を 0.0.0.0 で待ち受けさせ、初期設定のまま使い始めると、ログイン不要の操作画面や内部 API が外から到達可能になることがある。そこに AWS のアクセスキーや Kubernetes のサービスアカウントトークンが設定ファイルや環境変数として残っていれば、侵害はそのホストで終わらず、クラウド資源の横取りへ直結する。 対策の優先順位は、機能追加ではなく露出面の縮小になる。まずインターネット公開を前提にしないサービスは VPN や踏み台配下へ寄せ、やむを得ず公開するなら認証、IP 制限、レート制御を最初に入れる。次に、クラウド鍵やトークンは短命化し、用途ごとに分離し、再利用できない設計へ寄せる。さらに、公開資産の棚卸しを Shodan のような外部視点でも確認し、自組織が想定していない待受けを定期的に洗い出す必要がある。 具体例を挙げると、研究用の n8n を社外から触れるように置いた後、Webhook の検証や API テストのために AWS キーを環境変数へ入れたままにすると、侵害者は設定ファイルやプロセス情報から認証情報へ到達しやすくなる。最初の侵入口は AI でも、自動化基盤でも、最終的には認証情報の回収と再利用に集約される。だからこそ、公開前の「機能確認」だけでは足りず、公開後の「何を奪われるか」を基準に設計する姿勢が必要になる。
