VU#382143: Lowcoder Query Library API contains cross-tenant authorization bypass allowing for data exfiltration

概要

Lowcoder 2.4.10のQuery Library APIで、組織をまたぐ認可確認が欠落し、認証済みのadminまたはdev権限を持つ利用者が、別組織の非公開クエリ情報を取得・実行できる脆弱性が確認された。CVE-2026-16753が割り当てられているが、記事にCVSSスコアの記載はない。問題はメタデータ取得とクエリ実行の各APIで、利用者のロールは確認する一方、要求対象のクエリが同じ組織に属するかを検証しない点にある。攻撃者はクエリ設定全体や参照先データソースの識別子を読み取り、他組織のバックエンドにあるデータを取得できるほか、クエリの内容によってはデータ変更・削除や、他組織の費用負担で有料データソースを利用する事態にもつながる。特に複数組織を同一インスタンスで運用し、自己登録時にadminまたはdev権限が付与される設定では、攻撃の入口が広がるため、対象APIへのアクセス制限、権限棚卸し、テナント分離を優先したい。確認されたのはバージョン2.4.10で、公式修正は示されておらず、実際の悪用状況や他バージョンへの影響範囲も未確認となる。

📌 キーワード解説

テナント境界（tenant boundary）

同じサービスを共有する組織間で、データや操作権限を分ける境界を指す。認証済みでも、別組織の資源に触れられない認可が必要となる。

認可バイパス（authorization bypass）

利用者の権限確認や資源の所属確認が不十分で、許可されない操作が通る状態を指す。認証の突破とは異なり、ログイン後の権限判定が焦点となる。

ドメイン固有言語（DSL）

特定の用途向けに定義された設定・命令の表現形式を指す。ここではクエリの全設定が含まれ、結果データだけでなく接続先や処理内容の漏えいにもつながる。

深掘り解説

ロール確認とテナント所属確認を分けて設計する

ロール確認は「この利用者に管理者相当の操作を許すか」を判定するが、「この資源が利用者の組織に属するか」は別の確認となる。両者を一つの判定として扱うと、権限のある利用者が別テナントの資源へ到達する抜け道が残る。APIごとに、認証主体から組織識別子を確定し、対象資源の組織識別子と照合してから処理する必要がある。たとえばクエリ実行APIがクエリIDだけで処理を開始する実装なら、別組織のIDを指定して実行される可能性がある。メタデータ取得と実行の双方で同じ所属確認を行い、識別子を推測しにくくするだけの対策に依存しないことが重要となる。
