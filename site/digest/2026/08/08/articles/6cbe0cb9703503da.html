深掘り解説

CI/CDの秘密情報は「使う場所」より「残る場所」で管理する

CI/CDの秘密情報は、利用時の便利さよりも、どこに残りうるかで危険度が決まる。特に runner secret のように自動実行環境へ置く情報は、ビルドログ、環境変数、キャッシュ、成果物のどこかに意図せず滞留しやすい。 実務では、秘密情報を「一度読めれば十分」な前提で扱うと事故が起きる。たとえば、GitHub Actions で npm パッケージの公開権限を持つトークンを使っていた場合、ワームがそのトークンを抜けば、次の悪性版を正規の更新に見せて配布できる。すると感染点は1台の runner では終わらず、依存している利用組織へ連鎖する。 対策の要点は、権限分離と寿命短縮に尽きる。公開専用トークンを分ける、OIDC 連携で短命化する、secret を持つジョブを必要最小限にする、成果物やログから秘密が漏れないかを点検する、という流れになる。加えて、秘密情報の漏えいを前提に、公開パッケージの不審な再公開や GitHub Actions の設定変更を検知できる運用が必要になる。 具体例として、npm の公開ワークフローで「テスト用」と「本番公開用」を同じジョブに置いていると、悪性コードの実行権限と公開権限が同居する。そこを分けていれば、侵入者がテスト側を奪っても即座に悪性版を配布する難度は上がる。CI/CD では“動くか”より“漏れたら何が起きるか”を先に見る必要がある。
