VU#431093: TCG TPM 2.0 reference code found vulnerable to information leakage and timing side-channel attacks

Impact判定理由

ローカルの特権アクセスが前提でも、TPM 管理下の RSA 鍵の復号や偽造 attestation につながるため、端末真正性と証明基盤に直撃する。単一端末の情報漏えいにとどまらず、認証や準拠判定の信頼を崩す余地がある点が重い。 CERT/CC の注意喚起であり、TPM 実装の更新適用が必要な公的情報源であるため、悪用現実性を踏まえてベース評価を引き上げた。外部からの即時大量攻撃というより、内部侵害後の横展開や信頼偽装のリスクを優先して見るべき事案になる。

概要

TCG の TPM 2.0 reference implementation に、情報漏えい と タイミング型サイドチャネル の2件の脆弱性が見つかった。攻撃者は TPM command interface に優先権のあるローカルアクセスを持つ前提で、細工した TPM コマンドを送り、RSA OAEP 復号の差分や鍵関連情報を引き出す。悪用に成功すると、TPM 管理下の RSA 鍵に対する暗号文や資格情報を復号でき、偽の TPM attestations を作る足掛かりにもなる。影響は実装形態に左右され、ディスクリート TPM だけでなく fTPM や仮想化・クラウドの software TPM も対象になり得る。現時点で、どの製品・どの構成がどこまで影響するかはベンダー更新の適用状況を個別確認する必要がある。

📌 キーワード解説

タイミング型サイドチャネル

処理時間の差から秘密情報を推測する手法。正規の復号処理とは違い、エラーを出さずに漏れる点が厄介。

TPM attestation

端末が正規の TPM を使うと示す証明。単なる鍵保護ではなく、端末の信頼性判定に直結する。

RSA OAEP

RSA の暗号化方式の一つ。平文保護向けで、署名用 RSA と混同するとリスク評価を誤りやすい。

深掘り解説

TPM の弱点は「鍵そのもの」より「信頼の連鎖」を壊す点にある

TPM は鍵を外に出さずに守る装置として扱われがちだが、実務上の価値は鍵保護だけではない。起動測定、ディスク暗号化、証明、端末真正性の確認まで、信頼の起点として使われることが多い。 そのため、TPM の脆弱性は「秘密鍵が漏れるかどうか」だけで判断しにくい。たとえば、あるノート端末が TPM で端末証明を行い、社内 CA がその証明を信頼している場合、偽造 attestation が作れると、端末の健全性確認や ZTNA の前提が崩れる。鍵が直接盗まれなくても、証明の意味が失われれば認証基盤の設計が影響を受ける。 確認の軸は二つある。第一に、その TPM が本当に自組織の端末や VM で使われているか。第二に、TPM ベースの attestation や鍵発行が、認証・端末準拠・証明書発行のどこに接続しているか。ここが分かれると、同じ脆弱性でも「単一端末の問題」で済む場合と、「端末信頼の判定全体」を見直す必要がある場合に分かれる。 具体例として、社内配布の Windows 端末で fTPM を使い、MDM が TPM attestation を満たした端末だけに業務アプリを許可している構成を考える。この場合、パッチ未適用の端末が一台でも残ると、端末真正性の判定が迂回される余地が生まれる。逆に、TPM を暗号化専用に使っていて attestation を採用していないなら、主な関心は鍵素材の保護範囲と更新適用になる。
